# Component Design

コンポーネントは、UIの責務や状態、操作を独立して説明できる場合に分けます。ファイルの長さだけでは判断しません。

## 利用箇所の近くに置く

コンポーネント固有の状態や処理は、そのコンポーネントの近くに置きます。

入力値や処理中フラグなど、1つのUIだけで使う一時的な状態は、そのUIを担当するコンポーネントが持ちます。複数の子が参照・更新する状態や、親が更新結果をまとめるデータの管理元は、最も近い共通の所有者です。

```text
1つのUIだけで使う一時的な状態
→ そのUIを担当するコンポーネントが所有する

複数の子が使う状態や親がまとめるデータ
→ 最も近い共通の所有者に置く
```

親コンポーネントにすべての状態を集めず、実際に利用する場所へ置きます。親が管理する状態と`props`を必要以上に増やさないためです。

## コンポーネントを分ける基準

次のような境界が見えたときは、コンポーネントの分割を検討します。

- UIとして独立した責務を説明できる
- そのUIだけで使う状態がある
- submit、toggle、confirmなど独立した操作がある
- 親が子の表示や操作に関する細かな状態まで管理している
- `props`が増え、1つのコンポーネントが複数の役割を持ち始めている

例えばフォーム、一覧の1行、確認ダイアログは、それぞれ独立した操作や状態を持ちやすく、コンポーネントの境界にしやすい単位です。

単なる見出しや数行の静的なマークアップまで、機械的にコンポーネント化しません。名前を付けても独立した責務が増えないなら、親に残した方が読みやすい場合があります。

## 行数ではなく責務で分ける

ファイルが長いことは見直しのきっかけにはなりますが、行数そのものを分割基準にはしません。

巨大なコンポーネントの中に`renderForm()`や`renderList()`のような関数を増やしても、状態と責務の所有者が変わらなければ、設計上の分離にはなりません。

```tsx
function TaskDemo() {
  function renderForm() {
    // ...
  }

  function renderList() {
    // ...
  }

  return (
    <>
      {renderForm()}
      {renderList()}
    </>
  );
}
```

UIとして独立した責務があるなら、コンポーネントとして境界を作ります。

```tsx
function TaskDemo() {
  return (
    <>
      <TaskForm />
      <TaskList />
    </>
  );
}
```

同様に、状態を伴う処理をそのまま1つの巨大なカスタムフックへ移すだけでは、コンポーネントの境界や状態の所有者は変わりません。一方、複数のコンポーネントで再利用する場合や、状態を伴う処理を独立した責務として扱える場合は、カスタムフックが適しています。

## 状態は必要最小限にする

同じ情報を複数の状態へ重複して保持しません。

例えば一覧データとは別に選択中のオブジェクト全体を保持すると、同じデータが2か所に存在します。

```ts
const [tasks, setTasks] = useState<Task[]>([]);
const [pendingDelete, setPendingDelete] = useState<Task | null>(null);
```

選択状態として必要なのが識別だけなら、IDを保持して元データから導出します。

```ts
const [tasks, setTasks] = useState<Task[]>([]);
const [pendingDeleteId, setPendingDeleteId] = useState<string | null>(null);

const pendingDeleteTask = tasks.find((task) => task.id === pendingDeleteId) ?? null;
```

別の状態や`props`から計算できる値は、原則として新しい状態にしません。同じ情報の管理元を増やさず、状態を同期する必要がない設計にします。

## `props`が増えたら境界を見直す

`props`が増えてきた場合、1つのオブジェクトへまとめる前に、そのコンポーネントが複数の責務を持っていないか確認します。

例えば親が、

```text
input value
validation error
submitting
row pending
row error
dialog state
delete pending
delete error
```

をすべて管理し、それぞれを子へ渡しているなら、親が子の操作状態まで持ちすぎている可能性があります。

子だけで完結する状態は子へ移し、親は複数の子が共有するデータと画面構成に集中させます。

## 共有化は実際の重複が見えてから

機能固有のコンポーネントを、将来ほかでも使いそうという理由だけで共有コンポーネントへ移しません。

まず利用する機能の近くへ置きます。複数箇所で同じ責務が現れ、共通のAPIを説明できるようになってから共有化を検討します。

配置と共有層の依存方向は[Architecture](./architecture.md)を参照してください。

## Task機能の例

Task機能では、`TaskDemo`がTask配列と削除対象のIDを管理します。フォーム、一覧の1行、削除ダイアログは、それぞれの操作に必要な状態とエラーを持ちます。

## 判断するときの目安

コンポーネントを切り出すか迷った場合は、次を確認します。

```text
そのUIに独立した責務があるか
そのUIだけで使う状態があるか
独立した操作があるか
親が子の細かな状態まで管理していないか
同じ情報を複数の状態で保持していないか
```

複数当てはまるなら、コンポーネント境界を見直す価値があります。
単にJSXが長い、ファイルの行数を減らしたい、将来再利用するかもしれない、という理由だけでは分割や共有化を行いません。
